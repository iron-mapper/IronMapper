# Mapper comparison benchmarks

Comparison of IronMapper with other .NET object mappers: speed, allocations, cold start, NativeAOT compatibility,
size, and build time. Everything here can be reproduced with one script; the numbers of the last full run are in
**[results/RESULTS.md](results/RESULTS.md)**.

The specification of this suite is [BENCHMARK_SPEC.md](BENCHMARK_SPEC.md).

## Participants

| Id | Library | Mode |
|---|---|---|
| `Manual` | — | Hand-written code, the **baseline** of every comparison |
| `IronMapper` | IronMapper (NuGet) | Source generator: generated extension methods (`source.MapToXxx()`) |
| `IronMapper_IMapper` | IronMapper + IronMapper.Extensions.DI | `IMapper` from dependency injection (up to 1.1.x: reflection lookup, then `MethodInfo.Invoke` per call; from 2.0.0: the delegates of the generated registry) |
| `Mapperly` | Riok.Mapperly | Source generator: `[Mapper]` partial class |
| `Mapster` | Mapster | Runtime: own `TypeAdapterConfig`, `Compile()` in setup, `Adapt<TSource, TDest>(config)` |
| `AutoMapper` | AutoMapper | Runtime: `MapperConfiguration`, `CreateMapper()` in setup |

Exact package versions are pinned in [Directory.Packages.props](Directory.Packages.props) and listed in
`RESULTS.md` (written automatically, together with the machine, OS, .NET SDK and runtime, date and commit).

IronMapper is the published NuGet package by default. To measure the local sources in `../src` instead, set the
**environment variable** `UseLocalIronMapper=true` (MSBuild reads environment variables as properties; the scripts do
this). `-p:UseLocalIronMapper=true` is enough for `dotnet build` and `dotnet test`, **but not for measurements**:
BenchmarkDotNet builds the benchmark project again in a child process and passes no MSBuild property of the parent
`dotnet run`, so `dotnet run -p:UseLocalIronMapper=true -- --filter ...` measures the package of
`Directory.Packages.props` (1.1.3), while the child inherits an environment variable:

```powershell
$env:UseLocalIronMapper = 'true'      # bash: export UseLocalIronMapper=true
dotnet run -c Release -f net10.0 --project src/Comparison.Benchmarks -- --filter '*.NestedBenchmark.*'
```

Another published version: `IronMapperPackageVersion=<version>` (environment variable, with `UseLocalIronMapper` not
`true`).

## What is measured

| Area | How | Output |
|---|---|---|
| Runtime | BenchmarkDotNet, `[MemoryDiagnoser]`: Flat, Nested, Collection (10 / 1 000 / 100 000), CustomConfig, InPlace, DI overhead | `RESULTS.md` |
| Correctness | xUnit: every mapper's result equals `Manual`'s, deep copy, in-place; edge-case behavior is recorded, not judged | [results/feature-matrix.md](results/feature-matrix.md) |
| Cold start | Process start of a console per library (JIT and NativeAOT), plus BenchmarkDotNet `RunStrategy.ColdStart` in process | [results/startup.md](results/startup.md) |
| NativeAOT | Publish with `PublishAot=true`, trim/AOT warnings, does it run and print the right checksum, executable size | [results/aot.md](results/aot.md) |
| Size | `.nupkg` sizes and dependencies, framework-dependent publish size, AOT executable size | [results/footprint.md](results/footprint.md) |
| Build time | Generated projects with 50 and 200 entity/DTO pairs per library, `dotnet build --no-incremental` | [results/build-time.md](results/build-time.md) |

## Methodology and fairness rules

- **Same work.** Every mapper does the same work in the measured code: the same models, the same data, new objects
  for every nested object and collection. A scenario a library cannot do is marked N/A in the feature matrix; it is
  not made to fit by other means. Collections with the same element type (`List<string>` → `List<string>`) are kept
  out of the timed scenarios, because some libraries copy the reference and others create a new list.
- **Equivalence gate.** The benchmarks run only after `tests/Comparison.Tests` passes: for every mapper and scenario
  the result is structurally equal to `Manual`'s (`Assert.Equivalent(..., strict: true)`), and no object of the result
  is a reference to an object of the source.
- **Baseline `Manual`.** Plain hand-written code: object initializers, one small method per type,
  `new List<T>(count)` + loop, no argument checks. It was compared with the code generated by IronMapper and Mapperly
  in every scenario, both as C# and as JIT output (BenchmarkDotNet `DisassemblyDiagnoser`), and does no more work.
  Every table shows the ratio to `Manual`.
- **Why one method per type.** An earlier `Manual` mapped `Address` and `Product` with nested object initializers
  inside `MapCustomer` and `MapLine` (`Street = src.Address.Street, ...`). The C# work was the same as Mapperly's, but
  the larger IL kept the JIT from inlining: `MapLine` stayed a call for every order line and the `AddressDto`
  constructor a call per order, while Mapperly's small `MapToOrderLineDto` / `MapToProductDto` / `MapToAddressDto`
  were inlined into the loop. Mapperly measured 166 ns against 189 ns for `Manual` in Nested (ratio 0.88). With a
  method per type the JIT output of `Manual.MapNested` is a single method with no calls to mapping code, and the
  difference is gone: 165.9 ns `Manual`, 165.5 ns Mapperly (ratio 1.00, `launchCount = 3`). Collection with 10 orders
  went from 143.6 to 121.6 ns per order for `Manual`. Assignment order, list creation (`new List<T>(count)` + `foreach`), `Count`
  access and checks were the same in both and were not the cause.
- **Direct calls.** The benchmarks call each library directly (no shared interface, no virtual call), so nothing
  prevents the JIT from inlining generated code. The interface `IComparisonMapper` is used only in the tests.
- **Setup outside the measurement.** Data is generated deterministically (`new Random(42)`) in `[GlobalSetup]`;
  mapper configuration (Mapster `Compile()`, AutoMapper `CreateMapper()`, the DI container) is built there as well.
  Its cost is measured separately in the cold start benchmarks.
- **`launchCount = 3`.** Every benchmark runs in three separate processes and BenchmarkDotNet aggregates them. The
  result of one process depends on the decisions of Dynamic PGO: in CustomConfig the JIT output of `Manual` and
  Mapperly is identical, yet Mapperly measured ~6 % faster in every launch of one run, and the difference disappears
  with `DOTNET_TieredPGO=0` (ratio 0.98 ± 0.05); an early single-launch run had `Manual` at 82 ns instead of ~55 ns.
  A ratio slightly below 1 therefore does not mean that a library is faster than hand-written code.
- **Each probe references one library.** The cold start, NativeAOT and size probes (`probes/StartupProbe.*`) reference
  only their own library and use the same configuration source files as the benchmarks, so sizes and startup times
  are not mixed up between libraries. Every probe prints a checksum of the mapped order; a run counts only if the
  checksum equals the one of the Baseline console (no mapper) and of its own JIT build.

## How to read the results

- **Collection, 100 000 orders: the time is dominated by the garbage collector.** The result graph (~30 objects per
  order, ~3 M objects, ~160 MB) survives into Gen1/Gen2, and promotions and full collections cost more than the
  mapping code. Differences at this size mostly reflect how many bytes a library allocates.
- **For a clean comparison of the mapping code, use `Count` = 10 and 1 000.** `CollectionBenchmark` also shows
  `ns/item` and `B/item` (mean and allocated bytes divided by `Count`), so the sizes can be compared with each other.
- **Allocated (and `B/item`) is reliable at every size**: it does not depend on GC timing.
- **Cold start** has two parts: the process start of a console that sets up the mapper and maps one order
  (compare the Δ to the empty Baseline console, not the absolute time, which includes the launch overhead of the
  script), and the in-process BenchmarkDotNet cold start (configuration + first call, without process start).
- **Build time**: Δ to a project with the same models and no mapper. The source generators pay at compile time,
  the runtime mappers at startup; read it together with the cold start.
- Differences of a few percent between runs, or of a few tens of milliseconds between single builds, are noise.

## Caveats

- **`IronMapper_StaticFormat` is a workaround**, not the documented converter API. It maps the salary in
  CustomConfig with `MapFrom(s => SalaryFormat.Format(s.Salary))` instead of `UseConverter<SalaryConverter>()`, only
  to show the cost of creating the converter: up to 1.1.x the code generated for `UseConverter<T>()` calls
  `new T().Convert(...)` on every mapping; from 2.0.0 a converter without state (`SalaryConverter` is one) is created
  once and reused. The `IronMapper` row uses `UseConverter<T>()`, as a user would.
- **IronMapper up to 2.0 configures nested single objects through `MapFrom`.** IronMapper 2.0 does not map nested
  single objects automatically; the documented workaround is `ForMember(d => d.X, o => o.MapFrom(s => s.X.MapToXDto()))`
  per nested property (feature matrix: "manual setup"). The runtime benchmarks use exactly that with a package before
  2.1; with the local sources or a package 2.1 or later (`IRONMAPPER_NESTED_OBJECTS`, `Directory.Build.targets`) their
  profile maps them automatically. The generated build time projects (`run-build-time.ps1`) keep `ForMember` for every
  version.
  Collections of mapped types are automatic.
- **IronMapper collections** up to 1.1.x are generated as `Enumerable.ToList(Enumerable.Select(...))`; `Manual` and
  Mapperly use `new List<T>(count)` + loop. Part of the 1.1.3 collection difference to `Manual` comes from this. Under
  NativeAOT the same LINQ `Select` made the executable ~230 KB larger than with Mapperly, because it needs the NativeAOT
  runtime type loader (verified in isolation, see [results/baseline-1.1.3/aot.md](results/baseline-1.1.3/aot.md)).
  From 2.0.0 the generated code uses loops of a known size like `Manual` (no LINQ, no delegates).
- **Mapperly enumerates nested collections through `IReadOnlyCollection<T>`.** The generated
  `MapToListOfOrderLineDto(IReadOnlyCollection<OrderLineEntity>)` uses `foreach` over the interface. In Nested the JIT
  devirtualizes it for `List<T>` (guarded by a type check) and removes the boxed enumerator, so the allocation equals
  `Manual`'s. In Collection the whole `MapNested` is inlined into the outer loop and the boxed `List<T>.Enumerator` is
  allocated again for every order: +40 B per order in `B/item`, and part of Mapperly's time difference to `Manual`
  there (JIT output checked with `DisassemblyDiagnoser`).
- **`IronMapper_IMapper`** up to 1.1.x goes through reflection (`MethodInfo.Invoke` per call) and does not work under
  NativeAOT; from 2.0.0 it calls the generated methods through the delegates of the generated registry and works under
  NativeAOT. Collections use `MapCollection` + `ToList()` with both (`Map<List<T>>` works from 2.0.0, issue #8).
- **`Manual_DI`** (cold start only: `StartupBenchmark` and `probes/StartupProbe.Manual_DI`) is `Manual` resolved from
  the same Microsoft.Extensions.DependencyInjection container as `IronMapper_IMapper`. `IronMapper_IMapper` minus
  `Manual_DI` is what IronMapper adds on top of the container.
- **Mapster calls `Compile()` in setup.** All mappings are compiled up front, as recommended for production. Without
  `Compile()` Mapster compiles each type pair lazily on first use, so its cold start (and the first call of each
  pair) would be different from what is measured here.
- **Mapster.Tool is not measured.** Mapster also has a code generation path (Mapster.Tool, a `dotnet tool` run as a
  separate build step). All Mapster numbers are for the runtime configuration.
- **AutoMapper does not support NativeAOT**: it builds the mapping code at runtime. The AOT probe is published anyway
  to record the warnings and the failure.
- **Mapperly uses nullable annotations.** It generates `null` checks only for members declared nullable. The
  benchmark models declare nested objects and collections non-nullable (the timed data contains no `null`), so
  Mapperly emits no checks there; the feature matrix shows the `null` cases for both declarations.
- **AutoMapper license**: AutoMapper 16 reads a license key (`AUTOMAPPER_LICENSE_KEY` or `~/.automapper/license.txt`).
  Without it, it works but logs a license warning (asynchronously, ~1 s after start). Its package also brings
  `Microsoft.IdentityModel.*` as dependencies ([results/footprint.md](results/footprint.md)).

## What is not here, and why

- **Multi-threaded throughput.** Every mapper is stateless on the measured path; a parallel scenario would show
  nothing new.
- **Mapster.Tool (`Mapster_Codegen`).** It does not run as part of a plain `dotnet build`, which the specification
  requires for every participant.
- **Positional records, flattening, `null` handling in the timed scenarios.** Support differs between libraries
  (IronMapper does not compile positional records as destinations and does not flatten); the behavior is recorded in
  the feature matrix, not timed.
- **Other mappers.** The participants are fixed by the specification (BENCHMARK_SPEC.md, 2).
- **Other machines and operating systems.** One full run on one machine; the scripts work on Windows, Linux and macOS
  (PowerShell 7), so the numbers can be reproduced elsewhere.

## Requirements

- .NET SDK 10.0.4xx and PowerShell 7 (`pwsh`). For the .NET 8 run (see below): the .NET 8 runtime.
- NativeAOT toolchain: Windows — Visual Studio or Build Tools with "Desktop development with C++"; Linux — clang and
  zlib development files; macOS — Xcode command line tools.
- Windows: if `vswhere.exe` is not on `PATH`, the scripts add the Visual Studio Installer folder to `PATH` for the
  NativeAOT publish (`Initialize-NativeToolchain` in `scripts/BenchmarkCommon.psm1`; without it the link step fails
  with MSB3073 when `NoDefaultCurrentDirectoryInExePath` is set).
- At least 4 GB of free memory for the NativeAOT publish (`-LowMemory` compiles with one ILC thread).
- AutoMapper license key, see Caveats (optional).

## How to run

Everything, in order, then `results/RESULTS.md` (about 1.5 h on the reference machine; the script prints an
estimate and checks the environment first):

```bash
cd benchmarks
pwsh ./scripts/run-all.ps1              # full run
pwsh ./scripts/run-all.ps1 -Quick       # smoke test (~20 min): --job short, fewer runs, smaller N; not for publication
pwsh ./scripts/run-all.ps1 -CheckOnly   # only the estimate and the environment checks
pwsh ./scripts/run-all.ps1 -Dry         # checks that every command works (~5 min): --job Dry, 2 startup runs, N = 5
# A release run: the local sources into results/<version>, the published package into another folder.
pwsh ./scripts/run-all.ps1 -UseLocalIronMapper -ResultsDir results/2.0.0
pwsh ./scripts/run-all.ps1 -ResultsDir results/1.1.3-rerun
./scripts/run-all.sh                    # the same on Linux/macOS
```

A release run in one go (Windows; both runs one after the other in one session, the machine kept awake, build outputs
cleaned before each run, then a check of both reports; summary in `../artifacts/bench-summary.txt`), and the
comparison of the two runs, which `generate-report.ps1` embeds into the RESULTS.md of the second:

```bash
pwsh ./scripts/run-benchmarks.ps1        # published package -> results/1.1.3-rerun, local sources -> results/2.0.0
pwsh ./scripts/run-benchmarks.ps1 -Dry   # checks the commands (~10 min); results to ../artifacts/bench-dry/
pwsh ./scripts/compare-results.ps1 -Baseline results/1.1.3-rerun -Current results/2.0.0   # results/2.0.0/comparison.md
pwsh ./scripts/generate-report.ps1       # with IRONMAPPER_RESULTS_DIR=results/2.0.0: RESULTS.md with the comparison
```

`run-benchmarks.ps1` requires the branch `main` and a clean tree (changes under `benchmarks/results/` are allowed; with
`-Dry` both only warn). A run passes when `run-all.ps1` exits with 0, its log ends with "All done in", and its
RESULTS.md has none of the markers of a missing or shortened measurement (`_Not measured`, `**Quick run**`,
`**Dry run**`; case-sensitive). `-SkipRerun` keeps an existing `results/1.1.3-rerun`.

Close other applications and keep a laptop on mains power during the run.

Step by step:

```bash
dotnet build IronMapper.Comparison.slnx -c Release
dotnet test IronMapper.Comparison.slnx -c Release                       # gate (net10.0 and net8.0)
IRONMAPPER_WRITE_FEATURE_MATRIX=true dotnet test IronMapper.Comparison.slnx -c Release   # + feature-matrix.md (run-all.ps1 sets it)
dotnet run -c Release -f net10.0 --project src/Comparison.Benchmarks -- --filter '*.FlatBenchmark.*' --launchCount 3
pwsh ./scripts/run-startup.ps1 -Mode Both                               # startup.md (JIT, NativeAOT, BDN cold start)
pwsh ./scripts/run-aot.ps1 -ReportOnly                                  # aot.md from the NativeAOT run above
pwsh ./scripts/run-footprint.ps1                                        # footprint.md
pwsh ./scripts/run-build-time.ps1                                       # build-time.md (20 builds per project)
pwsh ./scripts/generate-report.ps1                                      # RESULTS.md
```

Raw outputs (BenchmarkDotNet artifacts in all formats, CSVs, publish logs, mstat files, published probes) go to
`results/raw/`, which is not committed; the `results/*.md` reports are.

A scenario can be measured again after a full run with the single command above. The Run row of `RESULTS.md`
then lists it with the time its measurement finished: the report compares the measurement files in `results/raw/`
with the end of the last `run-all.ps1`.

### .NET 8

The suite (`src/`, `tests/`) targets `net10.0` and `net8.0`; .NET 10 is the reference runtime of `RESULTS.md`. The
runtime scenarios run on .NET 8 with `-f net8.0`:

```bash
dotnet run -c Release -f net8.0 --project src/Comparison.Benchmarks -- --filter '*.NestedBenchmark.*' --launchCount 3
```

Their BenchmarkDotNet output goes to `results/raw/bdn-net8.0/` (the .NET 10 output stays in `results/raw/bdn/`, which
`generate-report.ps1` reads), and the feature matrix written by `dotnet test` on .NET 8 (with `IRONMAPPER_WRITE_FEATURE_MATRIX=true`) goes to
`results/raw/feature-matrix.net8.0.md`. `run-all.ps1` runs the runtime benchmarks on both (step `RuntimeNet8`, off
with `-SkipNet8`; RESULTS.md shows .NET 8 in its own section); the probes (cold start, NativeAOT, size) and the build
time projects are .NET 10 only.

`-ResultsDir <folder>` (relative to `benchmarks/`) writes the whole run — reports, raw data, BenchmarkDotNet artifacts,
the feature matrix — to that folder instead of `results/` (environment variable `IRONMAPPER_RESULTS_DIR`, read by the
scripts, `Program.cs` and the feature matrix test); its `raw/` is not committed. `-UseLocalIronMapper` measures the
local sources: the build, the tests and the runtime benchmarks through project references (`UseLocalIronMapper=true`);
cold start, NativeAOT, size and build time through the local sources packed as `<Version>-local.<timestamp>` into
`raw/local-packages` (MSBuild properties `IronMapperPackageVersion` and `IronMapperPackageSource`, see
`Directory.Packages.props`). A project reference is not what a package user gets: it copies the `.pdb` and XML docs into
the publish folder (the 2.0.0 run showed +107 KB instead of +48 KB) and rebuilds `../src` inside every timed
`dotnet build --no-incremental` (+1.2 s at any N). RESULTS.md lists IronMapper as "local sources" with the commit and
the package version used.

### Smoke check (CI)

The `benchmarks` job in `.github/workflows/ci.yml` builds the suite against the local sources, runs the equivalence
tests, and runs every runtime scenario once (BenchmarkDotNet `--job Dry`) on .NET 10 and .NET 8 — about a minute per
runtime. It checks that nothing is broken; it publishes no numbers. The same locally:

```bash
dotnet build IronMapper.Comparison.slnx -c Release -p:UseLocalIronMapper=true
dotnet test IronMapper.Comparison.slnx -c Release --no-build -p:UseLocalIronMapper=true
dotnet run -c Release -f net8.0 --project src/Comparison.Benchmarks --no-build -p:UseLocalIronMapper=true -- \
  --filter '*.FlatBenchmark.*' '*.NestedBenchmark.*' '*.CollectionBenchmark.*' \
           '*.CustomConfigBenchmark.*' '*.InPlaceBenchmark.*' '*.DiOverheadBenchmark.*' \
  --job Dry --join --artifacts ./results/raw/smoke-net8.0
```

The benchmark program exits with code 1 when a benchmark fails or a `--filter` matches nothing.

Note: the BenchmarkDotNet step of this smoke check passes `-p:UseLocalIronMapper=true`, which does not reach the child
build of BenchmarkDotNet (see above): that step runs the scenarios of the published package, not of `../src`. The build
and the equivalence tests do use the local sources.

### Quick A/B (`run-quick.ps1`)

The published release against the local sources, same machine, same session, same job:

```powershell
pwsh -NoProfile -File ./scripts/run-quick.ps1                     # Nested and InPlace, net10.0 and net8.0, 2.0.0 vs ../src
pwsh -NoProfile -File ./scripts/run-quick.ps1 -Filter '*.FlatBenchmark.*' -Frameworks net8.0 -PublishedVersion 2.0.0
pwsh -NoProfile -File ./scripts/run-quick.ps1 -CheckOnly           # only the pre-flight checks
pwsh -NoProfile -File ./scripts/run-quick.ps1 -Dry                 # --job Dry: checks the commands in a few minutes
```

- Order: for each framework the published package, then the local sources; build outputs are removed and the project is
  built again before each variant. The variant is chosen with environment variables, so BenchmarkDotNet's child build
  gets it too. After the build and after each run (child build, `--keepFiles`) the script checks IronMapper by the
  restore of `Comparison.Mappers` (`project.assets.json`) and `IronMapper.dll`: published — the package `IronMapper
  <version>`, no project reference into `../src`, the bytes of the package's `lib/*/IronMapper.dll`, `<version>+<commit
  of tag v<version>>`; local — the project reference to `src/IronMapper`, no IronMapper package, `+<HEAD>`, and in the
  build (not the child build, which compiles `../src` into its own folder with another embedded PDB path) the bytes of
  `src/IronMapper/bin/Release/*/IronMapper.dll`. The generator is an analyzer and is not copied to the build output, so
  it is not checked there; `Directory.Build.targets` switches it together with IronMapper. A wrong build stops the
  script, a wrong child build marks the run INVALID.
- Job: the one of the full run (default job, `--launchCount 3`), because one process varies by more than the effects
  looked for (Dynamic PGO, see Caveats); the numbers are comparable with `results/<release>/`. About 75 s per benchmark
  case and variant: the default (12 cases × 2 variants × 2 frameworks) takes about an hour.
- Pre-flight: branch (`-Branch`), commit and uncommitted changes (recorded with a hash of the diff), tag
  `v<PublishedVersion>`, SDK and runtimes, free memory, AutoMapper license, and that the restored package is the one on
  nuget.org (source in `.nupkg.metadata`, SHA-512 of the cached `.nupkg` equals the one downloaded from nuget.org).
- Output: `../artifacts/quick/<yyyyMMdd-HHmmss>/<published|local>-<framework>/` (BenchmarkDotNet artifacts, `build.log`,
  `run.log`, `assemblies.json`), `run-info.json`, `summary.md` (Mean, Ratio to `Manual` and Allocated of both variants
  and the difference). `benchmarks/results/` is not written. `-SummarizeOnly <run folder>` writes `summary.md` again.

These numbers are for a decision in a PR, not for publication: the published numbers come only from the full run.
