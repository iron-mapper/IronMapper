# IronMapper — план развития

Живой документ. Восстановлен 18.10.2026 из истории работы: план от 18.10, отчёты Claude Code о его изменениях (пункты 2.7–2.12, 3.5, «класс-маппер»), итоговый аудит `IRONMAPPER_IMPROVEMENTS.md` (пункты помечены «аудит п.N») и результаты бенчмарков `benchmarks/results/RESULTS.md` (1.1.3, .NET 10).

Если найдётся версия с другого компьютера — сверить с этой и объединить.

---

## Цель

IronMapper — способ уйти с AutoMapper, сохранив свои профили: `MappingProfile`, `CreateMap`, `ForMember`, `IMapper` продолжают работать, но код генерируется при сборке. Главный ориентир по качеству — **Mapperly** (тоже source generator, бесплатный, именно с ним будут сравнивать). AutoMapper — ориентир по возможностям для мигрирующих.

**Критерий успеха:** проект на AutoMapper 14 с типовыми профилями переезжает заменой пакета, `using` и базового класса профиля. Всё, что не переезжает, сообщается диагностикой `IMxxxx` с указанием строки в коде пользователя, а не ошибкой компиляции внутри сгенерированного файла.

## Правила работы

### Git

- Claude Code **не выполняет** `git commit`, `git push`, `git tag`. `git add` разрешён.
- Один пункт плана — одна ветка — один PR. Ветки: `fix/…`, `feature/…`, `chore/…`, `docs/…`, `release/…`.
- Слияние в `main` только через PR, способ — **squash**.
- CI (`ci.yml`) на push — только `main`; остальные ветки проверяются через `pull_request` (все job'ы, включая обязательные проверки ruleset «Build & Test» и «Pack & verify», а также `aot` и `benchmarks`). Ветку без PR CI не проверяет — открыть PR (можно черновик).
- Теги `v*` ставятся только на `main` после слияния; пуш тега запускает публикацию на NuGet.
- Новая ветка — всегда от актуального `main`. Если две ветки трогают одни файлы — сливать по очереди, вторую обновлять `git merge origin/main`.

### Порядок работы над пунктом

1. Воспроизвести проблему тестом, который падает. Если не падает — отметить в плане и идти дальше.
2. Исправить.
3. `dotnet build IronMapper.slnx -c Release` без предупреждений, `dotnet test IronMapper.slnx` зелёный.
4. Упаковку и CI проверять **только на чистом дереве**: сначала `git add -A`, затем `git clean -xdf -e .claude/ -e IRONMAPPER_PLAN.md`, затем `./eng/verify-package.ps1 -PackageDir ./artifacts/packages`.
5. Изменения в сгенерированном коде видны в snapshot-тестах (`*.verified.cs`). Бенчмарки в PR не запускаются (см. «Бенчмарки» ниже); изменённый снимок — пометка для полного прогона перед релизом.
6. Документация (EN и RU вместе) и `CHANGELOG.md` (`[Unreleased]`) — в том же PR.
7. Отметить пункт в этом плане.

### Бенчмарки

- В PR бенчмарки **не запускаются** (ни полные, ни частичные замеры). В PR достаточно smoke-проверки набора: job `benchmarks` в CI (сборка на локальных исходниках, тесты эквивалентности, одна итерация каждого runtime-сценария на net10.0 и net8.0); локально — то же самое, если менялся сам набор.
- Полный прогон (`benchmarks/scripts/run-all.ps1`) — отдельная задача перед релизом, когда весь код релиза в `main`. Цифры в README, `docs/`, CHANGELOG и `benchmarks/results/` обновляются только по нему.
- Если цель PR сформулирована в цифрах, её проверяет полный прогон; в PR — только код и smoke-проверка. Причину недостигнутой цели ищут в отдельной задаче (`DisassemblyDiagnoser`), не подгоняя код под число.

### Ограничения

- Не читать и не копировать исходники AutoMapper 15+ (RPL-1.5). Поведение сверять с документацией и версией 14.x (MIT).
- Не добавлять зависимости в основной пакет `IronMapper`.
- Не ослаблять `TreatWarningsAsErrors` и не отключать тесты ради зелёной сборки.

### Честная документация

- Каждое утверждение в README, `docs/`, XML-комментариях и метаданных пакета подтверждается кодом, тестом или бенчмарком.
- Цифры производительности — только из `benchmarks/results/`. Не утверждать превосходство, если разница в пределах разброса.
- «Known limitations» в обоих README убираются только вместе с исправлением.
- CLAUDE.md описывает фактическое состояние.
- Перед релизом обновить Roadmap сайта (`site/pages/roadmap.md` и `site/pages/ru/roadmap.md`, дата обновления в тексте) — единственный текст сайта, который пишется руками; остальное сайт берёт из `docs/`, README, CHANGELOG и `benchmarks/results/`.

### Сгенерированный код (аудит п.27)

- Не хуже того, что человек написал бы вручную: без LINQ, без делегатов в горячем пути, без лишних аллокаций, проверки на `null` только там, где тип допускает `null`.
- Никаких предупреждений компилятора внутри `.g.cs` (у пользователей с `TreatWarningsAsErrors` это ошибка, которую нельзя исправить).
- Только API, доступные в компиляции пользователя (проверять наличие, например `CollectionsMarshal`, `ArgumentNullException.ThrowIfNull`, `ModuleInitializerAttribute`).
- Маленькие методы на каждый тип (встраивание JIT), бросок исключений — через throw helper.

Явный опт-ин для конвертеров из других сборок (например, `[MapConverter(typeof(X), Cache = true)]`) — только по запросу пользователей |
| Уровень IM0001 / «строгий режим»        | **Решено 21.10.2026** (п.2.10, утверждено мейнтейнером): свойство `IronMapperStrictMapping` не вводится. Уровень любой диагностики задаётся стандартно — `dotnet_diagnostic.IM0001.severity = error` в `.editorconfig`/`.globalconfig`, `WarningsAsErrors`, `NoWarn`; проверено тестом (`ProfileUnmappedPropertyTests`, парсер `.editorconfig` компилятора) и в `verify-package` (сборка падает с IM0001 в строке `CreateMap`). Своё свойство дублировало бы механизм, который пользователи уже знают, и не действовало бы на отдельные файлы. | `ReverseMap()` и IM0001                  | **Решено 21.10.2026** (п.2.10): обратный маппинг не проверяется — он сопоставляет только по именам, `ForMember` к нему не применяется, исправить замечание можно было бы только заменой `ReverseMap()` на `CreateMap`; так же в AutoMapper (обратный маппинг создаётся с `MemberList.None`). | `AddConverter<T>()` в 3.0               | **Решено 21.10.2026** (п.1.5): в 1.x API не трогается, docs и XML-комментарий явно говорят, что на маппинг он не влияет. | Генерировать только используемые методы | **Отклонено** (20.10.2026). Чтобы знать, какие `MapToX`/`MapToXList`/`MapToXArray` вызываются, генератору пришлось бы сканировать все вызовы в компиляции: такой шаг зависит от каждого файла и ломает инкрементальность (перегенерация на каждое нажатие клавиши), а для `public`-методов, которые вызывают другие сборки, использование вообще не видно. Вместо этого: `[ExcludeFromCodeCoverage]` по свойству и отключение перегрузок (2.13) |
| Вложенный тип без карты                  | **Решено 23.10.2026** (мейнтейнер, релиз 2.1.0): ошибка **IM0002** по умолчанию, с понятным сообщением — какая пара типов (свойство источника → свойство приёмника, их типы) и что добавить (`[MapTo]`/`[MapFrom]` или `CreateMap<A, B>()`). Code fix «добавить карту для пары» — в том же PR, если получается без лишней сложности, иначе отдельным пунктом 2.1.0. Автоматический закрытый маппинг (как в Mapperly) — опция на будущее, **только по запросу пользователей** (п.3.4) |
| IM0004 (циклы)                           | **Решено 23.10.2026** (мейнтейнер): IM0004 — **Warning**, только для циклов, которые проходят хотя бы через одно одиночное вложенное свойство, смапленное автоматически (PR 2); свойство на пути цикла, настроенное явно (`MapFrom` или `Ignore`), разрывает цикл; циклы только через коллекции (деревья вроде `Category.Children`, которые работают уже в 2.0.0) не сообщаются. Причина: цикл типов не значит бесконечную рекурсию — она бывает только при цикле в данных (`Order.Customer.Orders`), а дерево через коллекцию собирается и работает в 2.0.0 (проверено пробой 23.10). Сообщение: цепочка типов, образующая цикл; что рекурсия бесконечна, только если цикл есть в данных; как разорвать (`Ignore`/`MapFrom`) и как подавить для заведомо конечных моделей вроде `Employee.Manager` (`#pragma warning disable IM0004` или `dotnet_diagnostic.IM0004.severity` в `.editorconfig`). Условие: ни одна сборка, проходящая на 2.0.0, не получает новых предупреждений (с `TreatWarningsAsErrors` это поломка в минорной версии) — проверить и написать в отчёте PR 2. Защита в рантайме (`MaxDepth`, отслеживание уже смапленных объектов) в 2.1.0 не делается — п.3.4 |
| Вложенные объекты: in-place и `null`     | **Решено 23.10.2026** (мейнтейнер, приёмка PR 2 с двумя изменениями до коммита — после 2.1.0 они были бы ломающими): (1) in-place **обновляет существующий вложенный объект** (`destination.X` не `null` — закрытый in-place `…Core` пары, рекурсивно; `null` — новый объект; struct — присваивание), закрытый in-place `…Core` генерируется и при `IronMapperGenerateInPlace=false`. Причина: DTO → сущность EF — замена отслеживаемой навигации новым экземпляром даёт вставку дубликата или конфликт отслеживания, у owned-типов — удаление и вставку. (2) `null` во вложенном свойстве, которое приёмник не допускает (навигация EF с `= null!` без `Include`; также источник без аннотаций), — проверка и `InvalidOperationException` из throw helper (`NoInlining`) с именами свойств источника и приёмника и подсказкой про `Include`, а не `NullReferenceException` внутри `…Core` |
| Элементы вложенных коллекций             | **Решено 23.10.2026** (мейнтейнер принял расхождение PR 2): элементы вызывают **публичный** `MapToX`, а не `…Core`. Причина: `ArgumentNullException` для `null`-элемента документирован в 2.0.0 (`docs/upgrading-to-2.0*.md`, `docs/advanced*.md`), закреплён тестом `CollectionShapeTests.NestedProperty_NullElement_ThrowsArgumentNullException` и AOT-пробой; перевод на `…Core` менял бы семантику в минорной версии. Публичный метод — проверка и вызов `…Core`, JIT встраивает его в цикл |
| Полный прогон бенчмарков для 2.1.0       | **Решено 23.10.2026** (мейнтейнер): по итогам 2.1.0 полный прогон бенчмарков (`run-all.ps1`/`run-benchmarks.ps1`, любые замеры BenchmarkDotNet) **не выполняется** — бенчмарки запускаются только по команде мейнтейнера. Тесты (`dotnet test`, тесты эквивалентности набора), `verify-package`, `verify-aot` и проверка на чистом дереве — как всегда, обязательно. Цели в цифрах (Nested, холодный старт `IMapper`) в этом релизе не проверяются и не объявляются достигнутыми; цифры в README, docs и `benchmarks/results/` остаются от 2.0.0; в CHANGELOG 2.1.0 — раздел Performance без цифр (только что изменилось в коде, с пометкой «не измерено»). В PR — по-прежнему smoke-проверка набора |
