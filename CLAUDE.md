# IronMapper — Claude Code Guide

## Project Overview

IronMapper is a **compile-time Object-to-Object mapper** for .NET — a free, open-source alternative to AutoMapper.
All mapping code is generated by a **Roslyn Incremental Source Generator** at compile time. Zero reflection at runtime.

## Projects

### `src/IronMapper` (netstandard2.0 + net10.0)
The **runtime** part of the library. Contains only:
- Attribute definitions (`[MapTo]`, `[MapFrom]`, `[Ignore]`, `[MapProperty]`)
- Public interfaces (`IMapper`, `ITypeConverter`)
- Base class `MappingProfile` for fluent configuration
- NO reflection-based mapping logic — only contracts

### `src/IronMapper.Generator` (netstandard2.0)
The **Roslyn Incremental Source Generator**.
- Registered as `[Generator]` implementing `IIncrementalGenerator`
- Reads `[MapTo]`/`[MapFrom]` attributes and `MappingProfile` subclasses from the compilation
- Emits strongly-typed `Mapper` partial classes with explicit property assignments
- Must target `netstandard2.0` (Roslyn generator host constraint)

### `tests/IronMapper.Tests` (net10.0)
Unit tests for the **runtime API**. References:
- `IronMapper` (normal project reference)
- `IronMapper.Generator` as `OutputItemType="Analyzer" ReferenceOutputAssembly="false"` — the generator runs during test compilation so generated code is exercised

### `tests/IronMapper.Generator.Tests` (net10.0)
Tests for the **generator itself** using `Microsoft.CodeAnalysis.CSharp` testing utilities.
Pattern: create an in-memory compilation, run the generator, assert on emitted source / diagnostics.

### `tests/IronMapper.Benchmarks` (net10.0, Exe)
BenchmarkDotNet benchmarks comparing IronMapper vs AutoMapper vs manual mapping.
Run only on `main` branch in CI (Release configuration).

## Architectural Decisions

### Why Source Generator instead of Reflection?

1. **Zero runtime overhead** — mapping code is ordinary C# compiled into the consuming assembly.
2. **Compile-time errors** — misconfigured mappings fail at `dotnet build`, not at `app.Run()`.
3. **AOT / NativeAOT compatible** — no `System.Reflection.Emit`, no dynamic IL.
4. **Debuggable** — generated `.cs` files can be stepped through in any IDE.
5. **Trimming safe** — no `[DynamicallyAccessedMembers]` annotations needed.

### Why `IIncrementalGenerator` not `ISourceGenerator`?

Incremental generators only re-run the affected pipeline stage when inputs change — critical for IDE responsiveness (no full recompile on every keystroke).

### Why `netstandard2.0` for the Generator?

The Roslyn compiler host (MSBuild / `dotnet build`) loads generator assemblies into a `netstandard2.0` context. The generator must target `netstandard2.0` regardless of the consuming project's TFM.
