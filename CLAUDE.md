# IronMapper — Claude Code Guide

## Project Overview

IronMapper is a **compile-time Object-to-Object mapper** for .NET — a free, open-source alternative to AutoMapper.
Mapping code is generated by a **Roslyn Incremental Source Generator** at compile time; the generated mappings
contain no reflection. Exception: `IMapper` from `IronMapper.Extensions.DI` still finds and calls the generated
methods through reflection (see [The DI path](#the-di-path-imapper)).

## Plan

`IRONMAPPER_PLAN.md` in the repository root is the working plan: rules, accepted decisions, status, release order and
the items with their "done when" criteria. **Read it before starting a task**, follow its rules, and mark what was done
(`[x]`, status, discrepancies found) in the same change. `git clean` below excludes it.

## Projects

### `src/IronMapper` (netstandard2.0 + net10.0)
The **runtime** package. Contains:
- Attributes (`[MapTo]`, `[MapFrom]`, `[Ignore]`, `[MapProperty]`, `[MapConverter]`)
- `MappingProfile` for fluent configuration (`CreateMap`, `ForMember`, `ReverseMap`, …); profiles are read by the
  generator, not executed for mapping
- Interfaces (`IMapper`, `ITypeConverter<TSource, TDest>`), exceptions
- `MappingValidator` — runtime validation through reflection (not used by generated code)

The package also ships `IronMapper.Generator.dll` and `IronMapper.CodeFixes.dll` in `analyzers/dotnet/cs`
(see `src/IronMapper/IronMapper.csproj`, target `IncludeAnalyzersInPackage`).

### `src/IronMapper.Generator` (netstandard2.0)
The **Roslyn Incremental Source Generator** (`IIncrementalGenerator`).
- Reads `[MapTo]`/`[MapFrom]` attributes and `MappingProfile` subclasses from the compilation.
- For every type pair emits extension methods into `IronMapper.Generated.GeneratedMappers`, one file per pair:
  - `MapToX(this Source source)` — new destination object;
  - `MapToX(this Source source, X destination)` — in-place update (skips `init` properties);
  - `MapToXList(this IEnumerable<Source>? source)` and `MapToXArray(...)` — collections.
- **Accessibility:** each method gets the minimum effective accessibility of its source and destination types
  (private/protected nested types → IM0010, not generated). `GeneratedMappers` is `public` if any method is public,
  otherwise `internal`; the modifier is declared once (`EmitClassDeclaration`).
- **Name collisions** (`Analysis/MappingPlanner.cs`): a type pair defined twice is generated once (IM0007; profile
  `CreateMap` wins over `ReverseMap`, `[MapTo]`, `[MapFrom]`). Two mappings from one source to destinations with the
  same simple name get qualified names — destination namespace/containing-type segments, then type arguments
  (`MapToAdminUserDto`, `MapToBoxOfInt32`), IM0013; if nothing is unique — IM0014, not generated.
- Must target `netstandard2.0` (Roslyn generator host constraint).
- **Pipeline data** (`Analysis/Models`) is compared by value: every collection is `EquatableArray<T>`, every model
  implements `Equals` over all its fields (diagnostics included); no `ISymbol`, `SyntaxNode`, `Location` or
  `Compilation` in it. A new field must be added to `Equals`/`GetHashCode`.

### `src/IronMapper.CodeFixes` (netstandard2.0)
Code fixes for IM0001 and IM0006. Not covered by tests yet.

### `src/IronMapper.Extensions.DI` (netstandard2.1 + net10.0)
Separate NuGet package. `AddIronMapper(...)` registers `IMapper` and the profiles; `IronMapperOptions`.

#### The DI path (`IMapper`)
`RuntimeMapper` scans loaded assemblies for `IronMapper.Generated.GeneratedMappers`, matches the generated methods by
signature and calls them with `MethodInfo.Invoke`. Consequences confirmed by the benchmarks: overhead and allocations
per call, exceptions wrapped in `TargetInvocationException`, and it fails under NativeAOT. Replacing it with a
generated registry is planned (`IRONMAPPER_PLAN.md`, 1.3).

Until then `AddIronMapper` and `RuntimeMapper` are `[RequiresUnreferencedCode]` (message in `TrimMessages.cs`), and
so is `MappingValidator` in the runtime package: the app gets IL2026 at its own call. The net10.0 builds of both
libraries use `IsAotCompatible`, so a new unannotated reflection use fails the build; the netstandard builds take the
attribute from `Polyfills/` (same full name, internal).

### `tests/IronMapper.Tests` (net10.0)
Runtime tests. References `IronMapper` and `IronMapper.Generator` as
`OutputItemType="Analyzer" ReferenceOutputAssembly="false"` — the generator runs during test compilation so the
generated code is exercised.

### `tests/IronMapper.Generator.Tests` (net10.0)
Tests for the **generator itself** using `Microsoft.CodeAnalysis.CSharp` testing utilities.
Pattern: create an in-memory compilation, run the generator, assert on emitted source / diagnostics.
Prefer tests that compile and run the generated code (`GeneratorTestHelper.RunGeneratorCompileAndRun`, `CompileProject`)
over assertions on the generated text. Also contains:
- `GeneratedCodeSnapshotTests` — snapshots of the generated code (Verify.SourceGenerators) in `Snapshots/` (see below);
- `GeneratorCachingTests` — incremental caching (`trackIncrementalGeneratorSteps`; step names in
  `src/IronMapper.Generator/TrackingNames.cs`); `IncrementalDiagnosticsTests` — diagnostics after an edit match a
  fresh run.

### `tests/IronMapper.Integration.Tests` (net10.0)
The generator together with `IronMapper.Extensions.DI` and `Microsoft.Extensions.DependencyInjection`.

### `tests/IronMapper.PackageConsumer` (+ `InternalLib`, `PublicLib`)
Reference the packed `IronMapper` package (`PackageReference`), not the projects; built by `eng/verify-package.ps1`.
Not in `IronMapper.slnx`.

### `tests/IronMapper.AotProbe`, `tests/IronMapper.AotProbe.DI` (net8.0 + net10.0)
Published with `PublishAot` against the packed packages by `eng/verify-aot.ps1` (CI job `aot`, ubuntu). `AotProbe`:
generated extension methods, zero trim/AOT warnings, the executable checks the mapped values. `AotProbe.DI`: must
report IL2026 on its `AddIronMapper` line and nothing else (not run). Not in `IronMapper.slnx`. Locally on Windows the
publish needs the Visual Studio C++ build tools.

### `benchmarks/` — comparison suite (net10.0 + net8.0)
IronMapper (extension methods and `IMapper`) vs **Mapperly, Mapster, AutoMapper** and hand-written `Manual`
(the baseline): Flat, Nested, Collection, CustomConfig, InPlace, DI overhead, cold start, NativeAOT, package/publish
size, build time, feature matrix. Own solution `benchmarks/IronMapper.Comparison.slnx` and own
`Directory.Build.props` (does not inherit the root one); not part of `IronMapper.slnx`.

- **Target frameworks:** the suite projects (`src/`, `tests/`) target `net10.0` and `net8.0`, so `dotnet run` needs
  `-f`. The probes (cold start, NativeAOT, size, build time) and `tools/` are `net10.0` only. Published results are
  .NET 10; .NET 8 BenchmarkDotNet output goes to `results/raw/bdn-net8.0/`.
- **IronMapper source:** by default the **published** package (version in `benchmarks/Directory.Packages.props`); add
  `-p:UseLocalIronMapper=true` (or the environment variable `UseLocalIronMapper=true` for the scripts) to measure the
  local sources.
- **Results:** `benchmarks/results/RESULTS.md` (generated by `scripts/generate-report.ps1`, do not edit by hand); the
  1.1.3 baseline is frozen in `benchmarks/results/baseline-1.1.3/`. Method and caveats: `benchmarks/README.md`.
- **CI (`benchmarks` job in `ci.yml`, every push and PR, ubuntu):** only a smoke check against the local sources:
  build, equivalence tests on net10.0 and net8.0, one iteration (BenchmarkDotNet `--job Dry`) of every runtime
  scenario on both TFMs (`StartupBenchmark` excluded). About 2.5 minutes; no numbers are published. The benchmark
  program exits with 1 when a benchmark fails or a filter matches nothing.
- **Numbers come only from a full run:** `pwsh ./scripts/run-all.ps1` (~1.5 h, one machine, nothing else running).

```bash
cd benchmarks
dotnet test IronMapper.Comparison.slnx -c Release -p:UseLocalIronMapper=true      # equivalence gate (both TFMs)
dotnet run -c Release -f net10.0 --project src/Comparison.Benchmarks -p:UseLocalIronMapper=true -- --filter '*.NestedBenchmark.*'
pwsh ./scripts/run-all.ps1            # full run -> results/RESULTS.md; -Quick for a shorter local run
```

## How to Run

```bash
# Build everything
dotnet build IronMapper.slnx

# Run all tests
dotnet test IronMapper.slnx

# Run tests with coverage
dotnet test IronMapper.slnx --collect:"XPlat Code Coverage"

# Pack and verify the NuGet packages (layout + consumer project)
pwsh ./eng/verify-package.ps1

# NativeAOT probes against the packed packages (net8.0, net10.0)
pwsh ./eng/verify-aot.ps1

# Comparison benchmarks (local sources); full run: pwsh benchmarks/scripts/run-all.ps1
dotnet run -c Release -f net10.0 --project benchmarks/src/Comparison.Benchmarks -p:UseLocalIronMapper=true -- --filter '*.FlatBenchmark.*'
```

### Rule: verify packaging and CI changes on a clean tree

Anything that touches packaging (`dotnet pack`, `.nupkg` layout, `eng/verify-package.ps1`) or CI
(`.github/workflows/*`, MSBuild targets, build order) must be verified only after
`git clean -xdf -e .claude/ -e IRONMAPPER_PLAN.md`. CI always starts from a fresh clone; leftover `bin/`/`obj/` from earlier
local builds hide missing build steps (e.g. a pack that only works because the generator DLL was
already built).

**Before any clean-tree check, run `git add -A` first (stage only, do not commit).** `git clean -x` deletes
untracked files, including new files that are not in the index yet (new tests, new sources).
`git add` is allowed; `git commit`, `git push` and `git tag` are not — the maintainer does those.

```bash
git add -A
git clean -xdf -e .claude/ -e IRONMAPPER_PLAN.md
dotnet build IronMapper.slnx -c Release
dotnet test IronMapper.slnx
pwsh ./eng/verify-package.ps1 -PackageDir ./artifacts/packages
```

### Snapshot tests of the generated code

`tests/IronMapper.Generator.Tests/GeneratedCodeSnapshotTests.cs` verifies the generated files and diagnostics of
typical scenarios against `tests/IronMapper.Generator.Tests/Snapshots/*.verified.*` (committed, LF line endings via
`.gitattributes`). `*.received.*` is the output of a failed run and is in `.gitignore`.

After an **intended** change of the generated code:

```bash
dotnet test tests/IronMapper.Generator.Tests --filter "FullyQualifiedName~GeneratedCodeSnapshotTests"
# review every Snapshots/*.received.* (diff against the .verified.* file), then accept them:
cd tests/IronMapper.Generator.Tests/Snapshots
for f in *.received.*; do mv "$f" "${f/.received./.verified.}"; done
```

(`DiffEngine_Disabled=true` stops Verify from opening a diff tool.) A new scenario creates `*.received.*` on the first
run and fails until accepted. Never accept snapshots without reading the diff.

**A changed `*.verified.cs` in a PR is a reason to check performance:** run the affected comparison benchmarks
(`benchmarks/`, with `-p:UseLocalIronMapper=true`, see above) and put before/after numbers in the PR description. The
generated code must stay no worse than a hand-written mapping (no LINQ or delegates in hot paths, no extra
allocations).

## Architectural Decisions

### Why Source Generator instead of Reflection?

1. **Zero runtime overhead** — mapping code is ordinary C# compiled into the consuming assembly.
2. **Compile-time errors** — misconfigured mappings fail at `dotnet build`, not at `app.Run()`.
3. **AOT / NativeAOT compatible** — no `System.Reflection.Emit`, no dynamic IL. Checked for the generated extension
   methods in CI (`eng/verify-aot.ps1`); the `IMapper` DI path is not compatible yet and warns (IL2026).
4. **Debuggable** — generated `.cs` files can be stepped through in any IDE.
5. **Trimming safe** — the generated code needs no `[DynamicallyAccessedMembers]` annotations (again, except `IMapper`).

### Why `IIncrementalGenerator` not `ISourceGenerator`?

Incremental generators only re-run the affected pipeline stage when inputs change — critical for IDE responsiveness (no full recompile on every keystroke).

### Why `netstandard2.0` for the Generator?

The Roslyn compiler host (MSBuild / `dotnet build`) loads generator assemblies into a `netstandard2.0` context. The generator must target `netstandard2.0` regardless of the consuming project's TFM.
