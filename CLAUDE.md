# IronMapper — Claude Code Guide

## Project Overview

IronMapper is a **compile-time Object-to-Object mapper** for .NET — a free, open-source alternative to AutoMapper.
Mapping code is generated by a **Roslyn Incremental Source Generator** at compile time; the generated mappings
contain no reflection. `IMapper` from `IronMapper.Extensions.DI` calls them through a generated registry of delegates
(see [The DI path](#the-di-path-imapper)).

## Plan

`IRONMAPPER_PLAN.md` in the repository root is the working plan: rules, accepted decisions, status, release order and
the items with their "done when" criteria. **Read it before starting a task**, follow its rules, and mark what was done
(`[x]`, status, discrepancies found) in the same change. `git clean` below excludes it.

## Projects

### `src/IronMapper` (netstandard2.0 + net10.0)
The **runtime** package. Contains:
- Attributes (`[MapTo]`, `[MapFrom]`, `[Ignore]`, `[MapProperty]`, `[MapConverter]`)
- `MappingProfile` for fluent configuration (`CreateMap`, `ForMember`, `ReverseMap`, …); profiles are read by the
  generator, not executed for mapping
- Interfaces (`IMapper`, `ITypeConverter<TSource, TDest>`), exceptions
- `MappingValidator` — runtime validation through reflection (not used by generated code)

The package also ships `IronMapper.Generator.dll` and `IronMapper.CodeFixes.dll` in `analyzers/dotnet/cs`
(see `src/IronMapper/IronMapper.csproj`, target `IncludeAnalyzersInPackage`), and `buildTransitive/IronMapper.props`:
`global using IronMapper.Generated` for C# projects with `ImplicitUsings`, off with `IronMapperImplicitUsings=false`,
and `CompilerVisibleProperty` for the generator's MSBuild properties (`IronMapperReportUnmappedInProfiles`,
`IronMapperGenerateInPlace/List/Array`, `IronMapperExcludeFromCodeCoverage`, `IronMapperGeneratedCodeAttribute`,
`IronMapperRegistration`);
`buildTransitive/IronMapper.targets`: the feature switch `IronMapper.Registration.IsSupported` (see
[The DI path](#the-di-path-imapper)), with `ILLink.Substitutions.xml` embedded in `IronMapper.dll`.

### `src/IronMapper.Generator` (netstandard2.0)
The **Roslyn Incremental Source Generator** (`IIncrementalGenerator`).
- Reads `[MapTo]`/`[MapFrom]` attributes and `MappingProfile` subclasses from the compilation.
- For every type pair emits extension methods into `IronMapper.Generated.GeneratedMappers_{AssemblyName}`, one file per pair.
  **Class name** (`Analysis/GeneratedClassName.cs`, from 2.0.0): every character of the assembly name that is not a
  letter, digit or `_` becomes `_`; a name longer than 64 characters keeps 55 and gets `_` + 8 hex FNV-1a of the full name;
  carried by `GeneratedCodeOptions.ClassName` (step `CodeOptions`), so every generated file uses it. Unique per assembly:
  with one name ArchUnitNET merged the generated types of two assemblies (`GeneratedTypeNamesArchitectureTests`). Hint
  names stay `GeneratedMappers.g.cs`/`GeneratedMappers.Registration.g.cs`. Methods:
  - `MapToX(this Source source)` — new destination object;
  - `MapToX(this Source source, X destination)` — in-place update (skips `init` properties);
  - `MapToXList(this IEnumerable<Source>? source)` and `MapToXArray(...)` — collections.
  `MapToX(source)` checks `source` for `null` and maps it. **`…Core` only where something calls it** (PR 7 of 2.1.0,
  `MappingPlanner.WithCoreUse`): `MappingPlanEntry.UsesCore` — a nested object, a converted value, a constructor or
  factory argument of a generated mapping (`MapperCodeEmitter.FindNestedEntry`) — splits it into the public check and the
  private `MapToXCore(source)` with the body (`MappingPlanEntry.CoreMethodName`: `{MethodName}Core`, or
  `{MethodName}Core{HelperScope}` when a mapping of the same source is named so), which nested objects call directly.
  `UsesInPlaceCore` — an existing nested object updated by a generated in-place body (`FindNestedInPlaceEntry`; followed
  through parents whose in-place body exists: public overload, `MapInto` of the registration, or their own in-place
  `…Core`) — does the same for the in-place overload (or its private `MapInto{scope}`) and
  `MapToXCore(source, destination)`. Otherwise one method with the check and the body, the code of 2.0.0 byte for byte
  (snapshot `NotNestedMapping_SameCodeAs200`, checked against the 2.0.0 package). The plan takes the overloads and
  `IronMapperRegistration` for this (step `Plan` combines `MethodSettings` and `RegistrationSettings`).
  The last three are optional (`GeneratedMethods`: MSBuild `IronMapperGenerateInPlace/List/Array`, per mapping
  `GenerateInPlace/List/Array` on the attributes or `GenerateMethods(...)` in a profile, `MappingDescriptor.MethodOverrides`).
  A turned-off in-place overload stays as `private static void MapInto{scope}(source, destination)` for the registration
  (none with `IronMapperRegistration=false`);
  a turned-off List/Array is passed as `null` to `MapperRegistry.Register`, and the registry loops over `map` itself
  (`MapperEntry`). `MapToX(source)` is always generated (nested collections call it). **An in-place overload that
  changes nothing** (`MappingDescriptor.InPlaceNoOpReason`: a value-type destination, `ConvertUsing`, no settable mapped
  property; `MappingPlanEntry.InPlaceIsNoOp`) is `[Obsolete(reason)]` (removed in 3.0.0), and the registration calls a
  private `MapInto{scope}` that throws `MappingException` (`EmitInPlaceStub`, also for a constructor or a factory); a
  referenced assembly's `[Obsolete]` in-place overload is never called for a nested object
  (`PropertyTypeCheck.IsUpdatedByExistingMethod`). Tests: `GeneratedCodeSizeTests`, `NoOpInPlaceMapperTests`. The class declaration
  (`EmitClassDeclaration`) carries `[GeneratedCode("IronMapper", <generator informational version>)]` (off with
  `IronMapperGeneratedCodeAttribute=false`) and, with `IronMapperExcludeFromCodeCoverage`, `[ExcludeFromCodeCoverage]` —
  once, for all partial parts. Snapshot tests scrub the
  version. Tests: `GeneratedMethodsTests`, `tests/IronMapper.Integration.Tests/TurnedOffOverloadsTests.cs`.
- **Code shape** (`CodeGeneration/MapperCodeEmitter.cs`): no LINQ and no delegates. The public `MapToX(source)`,
  `MapToX(source, destination)` and the private `MapInto{scope}` carry `[MethodImpl(AggressiveInlining)]` (constant
  `AggressiveInlining`) when they only check the arguments and call `…Core`: the .NET 8 JIT did not inline them (a call
  plus a jump on the hot path; .NET 10 did). `…Core` and a method with the body never get it: its size is the mapping's, so the JIT decides
  (`IRONMAPPER_PLAN.md`, п.5.2, "AggressiveInlining на публичных методах"). `MapToXList`/`MapToXArray` are
  one-line calls of the generic `MapElementsToList`/`MapElementsToArray<TSource, TDest, TMapper>` declared once in
  `GeneratedMappers.g.cs` (`EmitElementLoops`, only when a mapping has the overload), with a private
  `readonly struct ElementMapper{scope} : IElementMapper<S, D>` per mapping whose `Map` calls `MapToX` (the private
  interface is generated, not in the runtime package; a struct type argument gives a specialized, inlinable call; no
  static abstract members). The generic methods check for `T[]`, `List<T>`, `ICollection<T>` (loops with a known size).
  Nested collection helpers (`MapCollection_*`) stay per property. Tests: `ElementLoopTests`, `CollectionShapeTests`. A nested collection property is mapped by a
  private helper `MapCollection_{Prop}{scope}` chosen by the declared source type (`SymbolHelpers.GetCollectionSourceKind`);
  an `IEnumerable<T>` destination stays lazy (iterator). Null checks: `ArgumentNullException.ThrowIfNull` when the
  user's compilation has it, otherwise the throw helper in `GeneratedMappers.g.cs` (`[DoesNotReturn]` if available) —
  `Analysis/Models/GeneratedCodeOptions.cs`. Runtime tests of every collection kind: `tests/IronMapper.Tests/CollectionShapeTests.cs`.
- **Accessibility:** each method gets the minimum effective accessibility of its source and destination types
  (private/protected nested types → IM0010, not generated). The generated class is `public` if any method is public,
  otherwise `internal`; the modifier is declared once (`EmitClassDeclaration`). Without generated mappings only an
  empty `IronMapper.Generated` namespace is emitted (`EmitEmptyNamespace`), so the package's global using compiles.
- **Name collisions** (`Analysis/MappingPlanner.cs`): a type pair defined twice is generated once (IM0007; profile
  `CreateMap` wins over `ReverseMap`, `[MapTo]`, `[MapFrom]`). Two mappings from one source to destinations with the
  same simple name get qualified names — destination namespace/containing-type segments, then type arguments
  (`MapToAdminUserDto`, `MapToBoxOfInt32`), IM0013; if nothing is unique — IM0014, not generated.
- **Nested objects** (`PropertyTypeCheck.CheckNestedObject`, issue #23): a name-matched property whose types differ and
  are objects (`IsObject`) is mapped by the mapping of its pair — `PropertyMappingDescriptor.NestedMapMethod`,
  `MappingPairs` (the source type, its base types and interfaces → the destination type; empty when a referenced
  assembly maps it, then `source.X.MapToY()`), `NullHandling` (`Analysis/NullHandling.cs`: `is null ? null :` for a
  destination that accepts `null`; `Throw` — `source.X ?? NestedObjectIsNull<X>("…")` — for a non-nullable destination
  (`InvalidOperationException` naming both properties; the generic helper with `NoInlining` is declared once in
  `GeneratedMappers.g.cs` when `MappingPlanEntry.UsesNestedObjectCheck`); no check for a struct source; IM0002 for a
  nullable source and a non-nullable destination). In-place (`MapperCodeEmitter.EmitNestedUpdate`): an existing
  `destination.X` is updated by the in-place `MapToYCore(source.X, destination.X)`, `null` gets a new object;
  `PropertyMappingDescriptor.NestedUpdatesInPlace` (a class with an accessible getter; a pair of this compilation, or a
  referenced assembly's mapping with the public in-place overload — `PropertyTypeCheck.IsUpdatedByExistingMethod`, then
  `source.X.MapToY(destination.X)`) and, for a pair of this compilation, `MappingPlanEntry.CanUpdateInPlace` (no
  `ConvertUsing`, no mapped `init` property); otherwise a new object is assigned. Like a collection element, the IM0002 "no
  mapping for the pair" carries `IfNoMappingFor` and is reported only when the plan generates none of the pairs
  (`MapperCodeEmitter.IsMappingMissing`). Elements of nested collections keep calling the public `MapToX`

  object has a candidate diagnostic (`CycleProperty`); `CollectDiagnostics` reports it only when the property closes a
  cycle of generated mappings (`Analysis/MappingCycles.cs`: edges are nested objects and collection elements mapped
  automatically; none from a `ConvertUsing` mapping, so a pair converter closes no cycle), with the chain as the last message argument. Tests:
  `NestedObjectTests`, `CyclicMappingTests`, `tests/IronMapper.Tests/NestedObjectTests.cs` (in-place `ReferenceEquals`

- **Converters** (`Analysis/ConverterAnalyzer.cs`): `[MapConverter]`, `UseConverter<T>()`, `ConvertUsing<T>()`. A
  converter without state (class with a public parameterless constructor, no instance fields/field-like events/finalizer
  in its hierarchy except `object`, constructors without code, every type of the hierarchy in source) is reused through
  `ConverterCache<T>.Instance` — a private generic holder declared once in `GeneratedMappers.g.cs` when a generated
  mapping needs it (`MappingPlanEntry.UsesConverterCache`); any other converter is `new T()` per call. A converter the
  generated class cannot create → IM0015, mapping not generated. Runtime tests: `tests/IronMapper.Tests/ConverterCacheTests.cs`.
- **Creating the destination** (`Analysis/ConstructorSelection.cs`, issue #24, from 2.1.0): an accessible parameterless
  constructor or a struct → object initializer, as in 2.0.0. Otherwise a constructor with named arguments
  (`MappingDescriptor.UsesConstructor`, `ConstructorArguments`: `PropertyMappingDescriptor`s whose `DestPropertyName` is
  the parameter name; `AllValueMappings` = arguments + properties), the other properties in an initializer after it. The

### `src/IronMapper.Extensions.DI` (netstandard2.1 + net10.0)
Separate NuGet package. `AddIronMapper(...)` registers `IMapper` and runs the generated registration of the given
assemblies (profiles are not added to the container); `IronMapperOptions`.

#### The DI path (`IMapper`)
No reflection over the generated code. For every assembly with mappings the generator emits
`GeneratedMappers.Registration.g.cs` (`MapperCodeEmitter.EmitRegistration`): a `[ModuleInitializer]`
`RegisterIronMapperMappings()` hands a callback to `IronMapper.Registration.MapperRegistry.AddAssembly`; the callback
calls `MapperRegistry.Register<TSource, TDest>(map, mapInto, mapList, mapArray)` with lambdas that call the generated
methods. `AddAssembly` only pushes the callback on a lock-free list (`MapperRegistry.PendingAssemblies`, no static
field initializers there, so the registry's dictionaries are not created); the registry runs the pending callbacks on
first use (`EnsureInitialized`, called by the `RuntimeMapper` constructor and by every lookup), under a lock, and
callers wait until a running registration has finished. An app that never creates `IMapper` registers nothing; it
loads `IronMapper.dll` for the module initializer (`IsSupported` must live there for the trimmer). It fills
`MapperCache<TSource, TDest>.Map/MapInto` (exact pairs: `RuntimeMapper.Map<TSource, TDest>` is a static field read and
a delegate call) and a by-`Type` table for `Map<TDest>(object)`: base types of the source, and collections as the
destination type (`List<T>`, `T[]`, `IEnumerable<T>` and the interfaces of `List<T>`, issue #8). `AddIronMapper(assembly)`
runs the assembly's module initializer (`MapperRegistry.EnsureModuleInitialized`, `RuntimeHelpers.RunModuleConstructor`;
the registration still waits for the first `IMapper`); on a missing mapping `RuntimeMapper`
does the same for all loaded non-framework assemblies. C# 8 gets the registration without `[ModuleInitializer]`
(the user calls it); targets without `ModuleInitializerAttribute` get an internal copy (`GeneratedCodeOptions`).
NativeAOT: `tests/IronMapper.AotProbe.DI` (zero warnings, run). Tests: `tests/IronMapper.Integration.Tests/MapperRegistryTests.cs`.

The module initializer calls `AddAssembly` only `if (MapperRegistry.IsSupported)` (feature switch
`IronMapper.Registration.IsSupported`). `buildTransitive/IronMapper.targets` sets it to `false` for a
`PublishAot`/`PublishTrimmed` app without the DI package (the DI package's `buildTransitive/IronMapper.Extensions.DI.props`
sets `_IronMapperExtensionsDIReferenced`); `IronMapperRegistration=true|false` overrides it. `ILLink.Substitutions.xml`
makes the getter a constant for ILLink/ILC, so the registration, the registry and unused generated methods are
trimmed. With the switch off `RuntimeMapper`'s constructor throws (`MapperRegistry.EnsureSupported`).
`eng/verify-aot.ps1` checks for `RegisterIronMapperMappingsCore` in the ILC map file (NativeAOT) and in the trimmed probe
assembly (ILLink, `PublishTrimmed`); `eng/verify-package.ps1` checks the switch in `runtimeconfig.json`. The registry is
keyed by `Type` (nested `ConcurrentDictionary<Type, …>`): a `(Type, Type)` key is JIT-compiled at startup, and
`Clear()`/`IsEmpty` take every lock and start the event source of the concurrent collections.

`MappingValidator` in the runtime package is `[RequiresUnreferencedCode]`: the app gets IL2026 at its own call. The
net10.0 builds of both libraries use `IsAotCompatible`, so a new unannotated reflection use fails the build; the
netstandard builds take the attributes from `Polyfills/` (same full names, internal).

### Code style

`.editorconfig` is checked in the build of every project: `EnforceCodeStyleInBuild` and `AnalysisLevelStyle` in the root
`Directory.Build.props` (errors, `TreatWarningsAsErrors`) and in `benchmarks/Directory.Build.props` (warnings there; not
for the generated `probes/BuildProbe.*`, whose build is timed); `benchmarks/cli` (net10.0) has `EnforceCodeStyleInBuild`
in its own props. **`AnalysisLevelStyle` is required:** the `:warning` of an `option = value:warning` line applies in the
build only with an analysis level for style, which net5+ projects have by default and netstandard projects do not, so
without it the generator, the code fixes and the netstandard builds of the libraries are not checked at all (a probe
`if (b) return 1;` compiled silently). Fixes: `dotnet format style <solution> --diagnostics <IDs> --severity warn`.
Generated code in user projects is not affected (analyzers skip `<auto-generated>` files; the snapshots contain code the
rules would reject), and none of these settings is packed. Projects outside the solutions get it too (PackageConsumer,
AotProbe*), except `tests/IronMapper.PackageConsumer.ImplicitUsings`: its `Sources/` stand for a user's code and are
built with LangVersion 9 and 8 (no file-scoped namespace, no `new()`); its IDE0005 variants turn the check on themselves.

### Rule: verify packaging and CI changes on a clean tree

Anything that touches packaging (`dotnet pack`, `.nupkg` layout, `eng/verify-package.ps1`) or CI
(`.github/workflows/*`, MSBuild targets, build order) must be verified only after
`git clean -xdf -e .claude/ -e IRONMAPPER_PLAN.md`. CI always starts from a fresh clone; leftover `bin/`/`obj/` from earlier
local builds hide missing build steps (e.g. a pack that only works because the generator DLL was
already built).

**Before any clean-tree check, run `git add -A` first (stage only, do not commit).** `git clean -x` deletes
untracked files, including new files that are not in the index yet (new tests, new sources).
`git add` is allowed; `git commit`, `git push` and `git tag` are not — the maintainer does those.

```bash
git add -A
git clean -xdf -e .claude/ -e IRONMAPPER_PLAN.md
dotnet build IronMapper.slnx -c Release
dotnet test IronMapper.slnx
pwsh ./eng/verify-package.ps1 -PackageDir ./artifacts/packages
```

### Snapshot tests of the generated code

`tests/IronMapper.Generator.Tests/GeneratedCodeSnapshotTests.cs` verifies the generated files and diagnostics of
typical scenarios against `tests/IronMapper.Generator.Tests/Snapshots/*.verified.*` (committed, LF line endings via
`.gitattributes`). `*.received.*` is the output of a failed run and is in `.gitignore`.

After an **intended** change of the generated code:

```bash
dotnet test tests/IronMapper.Generator.Tests --filter "FullyQualifiedName~GeneratedCodeSnapshotTests"
# review every Snapshots/*.received.* (diff against the .verified.* file), then accept them:
cd tests/IronMapper.Generator.Tests/Snapshots
for f in *.received.*; do mv "$f" "${f/.received./.verified.}"; done
```

(`DiffEngine_Disabled=true` stops Verify from opening a diff tool.) A new scenario creates `*.received.*` on the first
run and fails until accepted. Never accept snapshots without reading the diff.

**Benchmarks are not run in a PR** (`IRONMAPPER_PLAN.md`, rules): a PR gets the smoke check of the suite (CI job
`benchmarks`); the full run (`benchmarks/scripts/run-all.ps1`) is a separate task before a release, and only it
updates the numbers in the docs. A changed `*.verified.cs` is noted for that run. The generated code must stay no
worse than a hand-written mapping (no LINQ or delegates in hot paths, no extra allocations).

## Architectural Decisions

### Why Source Generator instead of Reflection?

1. **Zero runtime overhead** — mapping code is ordinary C# compiled into the consuming assembly.
2. **Compile-time errors** — misconfigured mappings fail at `dotnet build`, not at `app.Run()`.
3. **AOT / NativeAOT compatible** — no `System.Reflection.Emit`, no dynamic IL. Checked in CI (`eng/verify-aot.ps1`)
   for the generated extension methods and for the `IMapper` DI path.
4. **Debuggable** — generated `.cs` files can be stepped through in any IDE.
5. **Trimming safe** — the generated code needs no `[DynamicallyAccessedMembers]` annotations.

### Why `IIncrementalGenerator` not `ISourceGenerator`?

Incremental generators only re-run the affected pipeline stage when inputs change — critical for IDE responsiveness (no full recompile on every keystroke).

### Why `netstandard2.0` for the Generator?

The Roslyn compiler host (MSBuild / `dotnet build`) loads generator assemblies into a `netstandard2.0` context. The generator must target `netstandard2.0` regardless of the consuming project's TFM.
